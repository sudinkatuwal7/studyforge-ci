## What happens on reload

The code is in QuizPanel.tsx:

1. **The page starts from scratch.** React state is empty again, and `QuizPanel` mounts.
2. **It checks `sessionStorage` once:**

## Why store only the id

- **The database is the source of truth.** The grade is computed and saved on the server. A copy kept in the browser could go stale, for example if you submitted the same quiz from another tab.
- **No answers kept in the browser.** If the page stored the full quiz with correct answers, anyone could read them in DevTools before submitting. That would break "explanations only after submission." With only the id stored, the server decides what you see: `GET /quizzes/{id}/` never includes answers, and `/results/` returns 404 until you submit.

## Why `sessionStorage` rather than `localStorage`

`sessionStorage` belongs to one browser tab. It survives a reload, but it's cleared when the tab closes, so a quiz from last week won't reappear. Course chat makes the same choice, so the two features behave the same way. The key includes the user id and course id, so a different account or course in the same tab doesn't pick up someone else's quiz.

### STUDENT
what are sessionStorage, localStorage called? what are other examples along with their types and their usages?

### AI
Together these are called **browser storage** (or client-side storage). `sessionStorage` and `localStorage` are the two parts of the **Web Storage API**. Both are key-value stores: keys and values are always strings, the methods are synchronous (`setItem`, `getItem`, `removeItem`), each site gets its own space of about 5 MB, and both can be read by any JavaScript running on the page.

## The main kinds

| Mechanism | Type | How long it lasts | Size | Typical use |
|---|---|---|---|---|
| **In-memory** (React state, JS variables) | Any JS value | Until reload | Limited by RAM | Data for the current screen, such as our quiz before the fix |
| **`sessionStorage`** | Web Storage, string key-value | One tab; survives reloads, cleared when the tab closes | ~5 MB | Per-tab progress: our quiz id, course chat sessions, half-filled forms |
| **`localStorage`** | Web Storage, string key-value | Until code or the user clears it, shared by all tabs | ~5 MB | Preferences: theme, language, dismissed banners |
| **Cookies** | Small strings sent with every HTTP request | Until an expiry date, or the end of the browsing session | ~4 KB each | Login sessions, CSRF tokens; the server reads them |
| **IndexedDB** | Asynchronous database of objects, with indexes and transactions | Long-term | Large (hundreds of MB or more) | Offline apps, big datasets, files and blobs |
| **Cache API** | Stored HTTP request/response pairs, usually used with a Service Worker | Long-term | Large | Offline pages and cached assets in Progressive Web Apps (PWAs) |
| **URL** (query string, `#hash`, route path) | Text in the address bar | As long as the link exists | ~2 KB to be safe | State that can be shared or bookmarked: `/courses/42`, `?tab=quizzes`, search filters |
| **History state** (`history.pushState`) | A JS object attached to a history entry | While that history entry exists | Small | Restoring scroll position or view on Back and Forward |
| **Origin Private File System (OPFS)** | A private file system for the site | Long-term | Large | Heavy apps such as in-browser editors and databases (for example SQLite compiled to WebAssembly) |

(WebSQL was an older browser database. It's deprecated and has been replaced by IndexedDB.)

## Choosing between them

- **Is it secret?** Keep tokens out of `localStorage` and `sessionStorage`, because any script on the page, including injected (XSS) code, can read them. Use an `HttpOnly` cookie, which JavaScript can't read.
- **Should another person or device see it?** Put it in the URL (shareable) or on the server (synced across devices).
- **Is it big or structured?** Use IndexedDB.
- **How long should it last?** Only this screen: memory. This tab: `sessionStorage`. Across visits: `localStorage` or IndexedDB.

- **Access token:** kept in memory only. courses.ts:12 says "we do not read localStorage".

### STUDENT
are these two browser storage only for react?

### AI
No. They have nothing to do with React. `sessionStorage` and `localStorage` are built into the browser itself, as part of the Web Storage standard. Any JavaScript running in a web page can use them, with or without a framework:

- Plain JavaScript, in a `<script>` tag
- React, Vue, Angular, Svelte, jQuery
- TypeScript, which compiles to the same JavaScript calls

The code looks the same in all of them:

```js
sessionStorage.setItem("quiz", "5");
sessionStorage.getItem("quiz");   // "5"
```

React only enters the picture in how StudyForge wires storage into components. For example, QuizPanel.tsx reads the stored id in a `useState` initializer and fetches the quiz in a `useEffect`. The `sessionStorage` calls themselves are ordinary browser code.

Where they **don't** exist:

- **On the server.** Django (Python) and Node.js (the JavaScript runtime outside the browser) have no `sessionStorage`. The browser holds it, so server code can't read it. That's why the backend never sees our quiz id unless the page sends it in a request.
- **In tests without a browser.** Vitest uses jsdom, which imitates a browser. That's why the new tests could call `sessionStorage.setItem(...)` and `sessionStorage.clear()`.
- **In native mobile apps.** iOS and Android have their own storage (UserDefaults, SharedPreferences, SQLite). React Native, for example, uses a separate library called `AsyncStorage` because the browser APIs aren't there.

The other kinds from the table (cookies, IndexedDB, the URL) are also browser features that any framework can use.
