### AI
Django REST Framework (DRF) turns your Django data into an API that the React frontend can call.

The confusing part is that **a Django model and a DRF `ModelViewSet` do different jobs**.

Think of our To-Do feature as four pieces:

| Piece | Job | Our example |
|---|---|---|
| **Model** | Defines database fields and relationships | `TodoItem` |
| **Serializer** | Validates incoming data and converts model objects into response data | `TodoItemSerializer` |
| **View** | Handles requests, checks access, and coordinates reading or saving | `TodoListCreateView` |
| **URL configuration** | Connects a URL to a view | `/api/v1/todos/` |

**1. The model defines what we store.**

```python
class TodoItem(models.Model):
    title = models.CharField(max_length=200)
    course = models.ForeignKey(Course, on_delete=models.CASCADE)
    is_completed = models.BooleanField(default=False)
```

This describes a task’s database structure. Django’s ORM lets us work with that table through Python:

```python
TodoItem.objects.filter(course__owner=request.user)
```

That means: “Find tasks whose course belongs to the signed-in user.” Django translates it into SQL.

The model does not create API endpoints.

**2. The serializer defines what the API accepts and returns.**

Our `TodoItemSerializer` validates submitted data—for example, whether the title is valid and the selected course belongs to the student.

```python
serializer.is_valid(raise_exception=True)
serializer.save()
```

The first line validates input and returns a `400` response if invalid. The second saves the validated task.

For responses, `serializer.data` turns model objects into simple data that DRF can render as JSON.

**3. The view handles the request.**

Our implementation uses **`APIView`, not a ViewSet**:

```python
class TodoListCreateView(APIView):
    def get(self, request):
        # List the student's tasks.
        ...

    def post(self, request):
        # Validate and create a task.
        ...
```

We explicitly write what happens for each HTTP method. Our separate `TodoCompletionView` handles `PATCH` requests.

**4. A `ModelViewSet` is an alternative that supplies common actions.**

Instead of writing each operation yourself, you can use:

```python
class TodoViewSet(ModelViewSet):
    serializer_class = TodoItemSerializer

    def get_queryset(self):
        return TodoItem.objects.filter(course__owner=self.request.user)
```

This is a simplified illustration, not a complete replacement for our code. Authentication and other restrictions still need configuration.

A `ModelViewSet` supplies these actions:

| HTTP request | Action |
|---|---|
| `GET /todos/` | List tasks |
| `POST /todos/` | Create a task |
| `GET /todos/7/` | Retrieve one task |
| `PUT /todos/7/` | Update a task |
| `PATCH /todos/7/` | Partially update a task |
| `DELETE /todos/7/` | Delete a task |

A DRF **router** can generate the URL mappings for those actions.

I chose `APIView` because your task needs three specific operations, including a PATCH that changes **only completion status**. It makes those rules explicit. `ModelViewSet` would also work, but we would need to restrict its default operations.

For our current creation endpoint, the flow is:

```text

→ URL selects the view
→ View checks authentication
→ Serializer validates the input and course ownership
→ Model saves the task in PostgreSQL
→ Serializer prepares the response data
→ DRF returns JSON with status 201
```
