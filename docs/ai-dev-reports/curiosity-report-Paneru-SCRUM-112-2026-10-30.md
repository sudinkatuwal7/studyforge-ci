**It's a TypeScript type error, not a bug in how the calendar behaves.** The popup should work fine in the browser, but the strict type check rejects one line, and that check is part of `npm run build`.

## What's wrong
This is the style object at CalendarMonth.tsx:305-310:

```tsx
style={{
  top: popupPlace?.top ?? 0,
  left: popupPlace?.left ?? 0,
  visibility: popupPlace ? "visible" : "hidden",
  "--tail": popupPlace ? `${popupPlace.tail}px` : "50%",   // line 309
}}
```

React's `style` prop has the type `CSSProperties`, which lists the standard CSS properties such as `top`, `left` and `visibility`. `--tail` is a custom CSS variable the app invented, so it isn't on that list. TypeScript treats any unknown key in an object like this as a likely typo, which gives this error:

```text
TS2353: Object literal may only specify known properties,
and '"--tail"' does not exist in type 'Properties<string | number, string & {}>'
```

## Why the code itself is fine
Aashish is using a normal technique: the JavaScript works out where the date is, and the stylesheet uses that value to aim the popup's pointer at it (Calendar.css:26):

```css
left: var(--tail, 50%);
```

React does set custom properties like this at runtime. The types just can't know that `--tail` is intentional.

## Why tests pass but the build fails

| Check | Does it check types? | Result |
|---|---|---|
| `npm test` (Vitest) | No, it strips types and runs the code | Passes |
| `npm run lint` (oxlint) | No | Passes, with warnings only |
| `npx vite build` alone | No | Passes |
| `npm run build` (`tsc -b && vite build`) | **Yes**, `tsc -b` runs first | **Fails** |

Because `tsc -b` fails, `vite build` never runs. Both the GitHub Actions and Bitbucket pipelines run `npm run build`, so this should fail on any branch that includes the line, including yours. I can't tell from here how it got merged, so check the CI result on PR #81.

## The fix
Tell TypeScript the object is intentional by adding a cast. This is the usual approach for CSS variables:

```tsx
import type { CSSProperties } from "react";

style={{

  left: popupPlace?.left ?? 0,
  visibility: popupPlace ? "visible" : "hidden",
  "--tail": popupPlace ? `${popupPlace.tail}px` : "50%",
} as CSSProperties}
```

This corrects what I suggested earlier: `as React.CSSProperties` is the same cast, but importing the type is clearer because I didn't see `CSSProperties` imported anywhere under `frontend/src`.

**A 422 means the request was well formed, but the server won't process it because of what it asks for.** Here, the student's selection is valid but has too much text to handle in one request.

## What it returns
The response comes from `CourseNotesView` in views.py:

```http
HTTP/1.1 422 Unprocessable Entity

{
  "code": "NOTES_INPUT_TOO_LARGE",
  "detail": "The selected materials are too long to process together. Select fewer."
}
```

- **On the backend:** the total length of the selected text is checked before any model call, so a rejected request costs nothing and saves nothing.
- **In the UI:** `NotesPanel` looks at `code` and shows "These materials are too long to combine at once. Select fewer and try again." The student's ticked materials stay selected, so they can untick some and retry.

## Why 422
The size problem can only be found after the server has read the materials from the database, so the status has to mean "understood, but can't process this".

| Status | Meaning | Why it doesn't fit |
|---|---|---|
| **400** Bad Request | The request itself is invalid | The IDs are valid. This API uses 400 for empty, duplicate or malformed lists. |
| **404** Not Found | The resource doesn't exist or isn't yours | The materials exist and belong to the student. |
| **409** Conflict | A conflict with the current state | This API uses it for materials that aren't ready or have no text. Those are problems with a material's state, while this one is about the selection. |
| **413** Content Too Large | The HTTP request body is too big | The body is only a short list of IDs. It's the stored text that's too large, and 413 could also be mistaken for an upload or proxy limit. |
| **503** Service Unavailable | A temporary server or provider failure | Retrying the same selection would fail every time, so 503 would wrongly suggest trying again. |
| **422** Unprocessable Content | Well formed, but can't be processed | It says the request was understood but this selection can't be processed, and it needs to change before retrying. |

## How much the choice matters
This is a judgment call, and 409 would also have been defensible since this API already uses it for material problems. The frontend looks at `code` first, so changing the status wouldn't change what the student sees.

The status still matters to anything that doesn't read `code`, such as logs and monitoring. It shows this as a client-side (4xx) problem to fix by changing the request, not a server outage (5xx).

**The number to watch is `out`.** For a full batch of about 10k tokens in, 900 to 3,000 out was normal. Something like `in=31718 out=399` is what the content loss looked like. A 201 alone doesn't prove the notes are complete, so count your planted facts too.
