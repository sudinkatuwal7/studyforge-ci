## 4.3: JSON list vs. a separate Option table

**What "heavier" means.** A separate table looks like this:

```python
class Option(models.Model):
    question = FK(Question, CASCADE, related_name="options")
    position = PositiveSmallIntegerField()
    text = TextField()
    is_correct = BooleanField(default=False)
```

That brings extra work:
- **More to build.** An extra model, migration and set of rules ("each question has exactly one correct option", "positions are unique").
- **Slower reads.** Loading a quiz means a second query, or `prefetch_related`, every time.
- **More complex writes.** Saving a 10-question quiz creates 10 questions plus about 40 options. SCRUM-42 would need nested serializers and a transaction to keep it all consistent.
- **Harder to enforce "exactly one correct answer".** A per-row database check can't do it. You'd need a partial unique constraint plus app code.

**Why I recommend the JSON list:**
1. **It matches how you'll use the data.** The AI produces a question with its options all at once. They're always read and written together and never edited one at a time.
2. **It matches what the team already does.** `StudyGuide` stores `key_concepts` and `important_points` as `JSONField` ([notes/models.py](backend/apps/notes/models.py)).
3. **The correct answer is a single number.** `correct_option_index`, checked to be within the list, makes "exactly one correct answer" impossible to break.
4. **It's enough for SCRUM-51.** Scoring is just `chosen_index == correct_option_index`. A future attempt or answer model can store the chosen index.

**When the Option table would be the better choice:**
- You need questions with several correct answers.
- You need per-option analytics, such as "how many students picked option B" through SQL.
- You need options that get edited or reused on their own.

None of those are in your Sprint 2 tickets. If one shows up later, a migration can convert the JSON to a table.

## 2. Walking through `models.py`

### `class Quiz(models.Model)`
Inheriting from `models.Model` turns the class into a database table (`quizzes_quiz`). Each field is a column:

- **`owner = ForeignKey(AUTH_USER_MODEL, ...)`**: the column stores the user's id.
  - `on_delete=CASCADE`: deleting the user deletes their quizzes.
  - `related_name="quizzes"`: lets you go the other way with `user.quizzes.all()`.
  - `settings.AUTH_USER_MODEL` points to the team's custom `users.User` instead of naming that class directly.
- **`course = ForeignKey("courses.Course", ...)`**: works the same way, giving you `course.quizzes.all()`. The `"app.Model"` string avoids importing the courses app.
- **`title = CharField(max_length=255)`**: required text.
- **`created_at` (`auto_now_add`)**: set once, when the quiz is created.
- **`updated_at` (`auto_now`)**: refreshed on every save.
- **`__str__`**: how a quiz is shown in the admin or shell. Here it shows the title.

There's no `id` field because Django adds one automatically (a `BigAutoField`, from `default_auto_field` in `apps.py`).

### `class Question(models.Model)`
- **`MIN_OPTIONS = 2`**: a plain class constant, not a column. `clean()` uses it.
- **`quiz = ForeignKey(Quiz, CASCADE, related_name="questions")`**: this is the one-to-many link. Deleting a quiz deletes its questions, and `quiz.questions.all()` lists them.
- **`position`**: the display order (1, 2, 3…). A `PositiveSmallIntegerField` is small and can't be negative.
- **`text`**: the question itself.
- **`options = JSONField(default=list)`**: stored as `["Height", "Width", ...]`. `default=list` passes the function rather than `[]`, so each row gets its own new list instead of all rows sharing one.
- **`correct_option_index`**: which option is correct. `0` means `options[0]`.
- **`explanation = TextField(blank=True)`**: `blank=True` means validation accepts an empty string.

### `class Meta`, and why it sits inside `Question`
`Meta` is Django's convention for settings about the model as a whole, as opposed to its individual fields. Django reads the nested class when it builds the model and stores the result in `Question._meta`. It's nested because it describes `Question` specifically. `Quiz` has no `Meta` because its defaults are fine.

- **`ordering = ["position"]`**: `quiz.questions.all()` comes back in position order without you writing `.order_by()`.
- **`UniqueConstraint(quiz, position)`**: one quiz can't have two "question 1"s.
- **`CheckConstraint(position >= 1)`**: positions start at 1.

Both constraints went into the migration, so **PostgreSQL itself enforces them**. They hold even if some code skips Django's validation.

### What `clean()` is
`clean()` is a hook Django provides for rules that involve more than one field, or that a column type can't express. Django calls it as part of `model.full_clean()`, along with the per-field checks. If a rule fails, it raises `ValidationError({"field": "message"})`, which attaches the error to that field.

- **`Quiz.clean()`**: the quiz owner must also own the course.
  - The `if self.course_id and self.owner_id` guard skips the check when either field is missing. The field checks report that error instead, rather than this method crashing.
- **`Question.clean()`** has two rules:
  - `options` must be a list of at least 2 non-blank strings.
  - `correct_option_index` must be less than `len(options)`.

**A correction to something I said earlier.** I told you serializers call `full_clean()`. That's true of Django's `ModelForm`, but **not of DRF's `ModelSerializer`**, which this project uses. DRF doesn't call `model.clean()`. So **`.save()` and DRF serializers both skip these rules**, and only the two database constraints always apply.

For SCRUM-42, the quiz-generation code should call `quiz.full_clean()` and `question.full_clean()` before saving. The alternative is to copy the same checks into the serializer's `validate()`. I can add one sentence about this to the schema doc if you want.

A foreign key stores the link on **one side only**. The `quizzes_quiz` table has an `owner_id` column, and the users table has no column listing quizzes. Django still lets you follow the link in both directions:

```python
quiz.owner             # forward: from a quiz to its user (reads quiz.owner_id)
user.quizzes.all()     # reverse: from a user to all their quizzes
```

`related_name` picks the name of that reverse accessor. Behind the scenes, `user.quizzes.all()` runs:

```sql
SELECT * FROM quizzes_quiz WHERE owner_id = <user.id>;
```

Without `related_name`, Django would make up the name `user.quiz_set`. Naming it `quizzes` reads better and matches the team's style: `Course.owner` uses `related_name="courses"`, giving `user.courses`.

The same applies to the other links:
- `course.quizzes.all()` returns a course's quizzes.
- `quiz.questions.all()` returns a quiz's questions.

SCRUM-42 and 51 will use these. For example, `course.quizzes.filter(owner=request.user)`.

## 2. Which `id`?

**Every model gets its own `id` primary key.** Each table has its own counter (1, 2, 3…), and the ids aren't shared between tables. "Quiz 5" and "User 5" are unrelated rows.

Foreign keys are **separate columns** that store another table's `id`. This is how the four tables look:

```text
users_user            courses_course           quizzes_quiz              quizzes_question
──────────            ──────────────           ────────────              ────────────────
id   (PK) ◄───┬────── owner_id (FK)            id        (PK) ◄───────── quiz_id (FK)
email         │       id (PK) ◄──────────────  course_id (FK)            id      (PK)
...           └─────────────────────────────── owner_id  (FK)            position, text,
                      name, ...                title, created_at, ...    options, ...
```

So you're nearly right, with one correction. A quiz's **primary key is `quiz.id`**. Its foreign keys are **two other columns**:
- `owner_id`, which stores the user's `id`
- `course_id`, which stores the course's `id`

A question likewise has its own `id` primary key, plus a `quiz_id` foreign key pointing to its quiz.

In Python, `quiz.owner_id` is the raw number in the column. `quiz.owner` loads the whole `User` object for that id, which costs an extra query the first time. That's why `clean()` compares `self.owner_id` instead of `self.owner`. Comparing the numbers is enough, and only `self.course` needs loading so it can read `course.owner_id`.

## 3. What `MIN_OPTIONS` is

It's a **plain class constant, not a database column**. Django only creates columns for attributes that are field objects (`models.CharField(...)` and so on). `MIN_OPTIONS = 2` is just an integer attached to the class, so it isn't in the migration.

It's used in one place, `Question.clean()`:

```python
or len(options) < self.MIN_OPTIONS
...
raise ValidationError({"options": f"Provide at least {self.MIN_OPTIONS} non-empty text options."})
```

So it sets **the minimum number of answer choices a question must have** (a multiple-choice question with one choice makes no sense). Keeping it as a named constant:
- puts the number in one place, so the check and the error message can't drift apart;
- lets other code reuse it, such as the SCRUM-42 prompt or a serializer (`Question.MIN_OPTIONS`), without hard-coding `2` again.

There's no maximum on purpose. SCRUM-42 can decide whether quizzes always have exactly 4 options.
