### 4. [DocumentStatus.tsx](/Users/aashishdhital20/Documents/studyforge/frontend/src/components/documents/DocumentStatus.tsx:12)

This component already polled the backend for document-processing updates. I added an optional callback:

```tsx
onStatusChange?: (document: StudyDocument) => void;
```

Whenever polling receives a new document state, it now both updates its internal display and tells the parent:

```tsx
setDocument(next);
notify.current?.(next);
```

The callback is stored in a ref:

```tsx
const notify = useRef(onStatusChange);

useEffect(() => {
  notify.current = onStatusChange;
}, [onStatusChange]);
```

Using a ref prevents the polling effect from restarting merely because React receives a newly created callback function during a render.

This creates the following update path:

```text
Backend polling
      ↓
DocumentStatus
      ↓
MaterialItem
      ↓
CourseMaterials shared list
      ↓
Pandu reference picker
```

For example, when `Lecture.pdf` changes from `PROCESSING` to `READY`, Pandu’s reference picker can show `READY` without another API request.

It also handles request states:


The separate component is not technically required. The application would work with everything in `CourseDetailPage`. It is a design choice that keeps data loading separate from workspace behavior, prevents the page component from growing too large, and gives the interactive course interface a clear testing and integration boundary.

### STUDENT
If the user's session expires after the course loads, what happens 

### AI
I’ll trace the authentication state and the course/material request handling so the answer reflects the actual expiry behavior rather than an assumption.

### AI
After the course has loaded, the page does **not immediately know** that the access token expired. The course workspace remains visible until another authenticated request is made.

What happens next depends on the action.

- **Status polling:** the next document-status request receives `401` or `403`. Polling stops and shows: “Your session has ended. Sign in again to check this document.”
- **Uploading:** the upload fails, displays an expired-session message, and disables further uploads for that rejected token.
- **Generating notes:** the request fails and displays: “Your session has ended. Sign in again to generate study notes.”
- **Renaming/deleting:** the request fails and the material card displays the returned request error.
- **Pandu demo:** it continues working because it currently uses only local React state and makes no authenticated backend request.

A key limitation is that most course APIs currently receive and use the access token directly:

```tsx
await request(path, options, accessToken);
```

Although `AuthContext` has an `authenticatedFetch` function that can refresh an expired access token, the course, document, upload, and study-guide APIs do not currently use it. Therefore, these requests do not automatically refresh the token or globally sign the user out.

The resulting behavior is:

```text
Access token expires
        ↓
Course remains visible
        ↓
Next backend operation returns 401
        ↓
That feature shows a session-expired error
        ↓
User remains on the workspace
```

If the session is cleared elsewhere—for example, logout or a rejected refresh through `authenticatedFetch`—then `user` becomes `null`. `App` stops rendering `AppShell` and shows the login page:

```tsx
if (!user) {
  return (
    <main className="auth-layout">
      <LoginPage />
      ...
    </main>
  );
}
```

Refreshing the browser also triggers `restoreSession()`. If the refresh cookie is still valid, the app gets a new access token and restores the course URL. If the refresh cookie has expired, the user sees the login page.

So the current implementation handles expiry safely at the individual feature level, but the user experience is inconsistent: the workspace can remain visible with several expired-session errors. A cleaner future improvement would route all authenticated course requests through the shared refresh mechanism, then redirect to login only when refreshing the session fails.

```tsx
const reference = useRef(initialValue);
```

React returns an object shaped like this:

```tsx
{
  current: initialValue
}
```

You read or update it through `.current`:

```tsx
reference.current = newValue;
```

The important difference from `useState` is:

| Hook | Persists across renders | Updating it rerenders UI |
|---|---:|---:|
| `useState` | Yes | Yes |
| `useRef` | Yes | No |

For example:

```tsx
const [count, setCount] = useState(0);
const request = useRef<AbortController | null>(null);
```

Changing `count` should update the page, so it uses state. Changing `request.current` is internal bookkeeping and should not redraw the page, so it uses a ref.

In the course workspace, `useRef` is used for several purposes.

### 1. Referencing an HTML element

In Pandu’s chat:

```tsx
const log = useRef<HTMLDivElement>(null);
```

The ref is attached to the message area:

```tsx
<div ref={log} className="chat-messages">
```

React places the actual `<div>` element in:

```tsx
log.current
```

When messages change, the code scrolls that element to the bottom:

```tsx
useEffect(() => {
  if (log.current) {
    log.current.scrollTop =
      log.current.scrollHeight;
  }
}, [props.messages, props.status]);
```

This is a common `useRef` use case: accessing a real DOM element.

The reference picker uses the same approach:

```tsx

```

The actual file input is hidden:


```tsx

</button>
```

Here, `input.current` is the real file-input element, and `.click()` opens the browser’s file picker.

`MaterialItem` uses:

```tsx

  useRef<AbortController | null>(null);
```

Before starting a rename or delete:

When the request begins:


When it finishes:


If the component unmounts, the active request is canceled:

```tsx
useEffect(
```

### 6. Keeping the latest status callback

In `DocumentStatus`:

```tsx
const notify = useRef(onStatusChange);
```

The ref is updated when the callback changes:

```tsx
useEffect(() => {
  notify.current = onStatusChange;
}, [onStatusChange]);
```

The polling code calls:

```tsx
notify.current?.(next);
```

This allows the polling loop to use the latest callback without restarting merely because the parent produced a new callback function during a render.

### 7. Remembering the latest document status

`DocumentStatus` also uses:

```tsx
const latest = useRef(tracked.snapshot);
```

After polling:

```tsx
latest.current = next;
```

The next polling decision can check:

```tsx
if (isTerminal(latest.current)) return;
```

This stores the most recent document object independently of React’s render scheduling.

A useful way to choose between the hooks is:

```text
Does changing the value need to update the screen?

Yes → useState
No  → useRef
```

Use `useRef` for DOM elements, timers, request controllers, counters, and internal bookkeeping. Use `useState` for messages, loading indicators, errors, selected tabs, or anything else the student should see change.
