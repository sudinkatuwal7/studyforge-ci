### STUDENT
Why store the React Router location key instead of a boolean for the mobile drawer?

### AI
Storing the key lets the drawer close on **any** navigation without code that watches the route. Your question also turned up a bug in what I gave you, explained below with the fix.

The problem: On phones, the drawer sits on top of the page. When the user goes somewhere else, it has to close. "Somewhere else" can mean: tapping a link in the drawer, the browser Back/Forward buttons or Android's back gesture, code calling `navigate()` (after sign-out, for example).

What a plain boolean would need: Nothing knows the route changed, so you'd add one of these:
1. `onClick={() => setNavOpen(false)}` on every link. This misses Back/Forward and `navigate()`. Every link added later also has to remember it.
2. A `useEffect` that closes the drawer when `location` changes. This catches everything, but it runs after paint. The new page renders with the drawer still open, then a second render closes it, so there's a visible flash. React's docs call this pattern out as one to avoid ("You Might Not Need an Effect"), and React 19's hooks lint flags calling `setState` inside an effect.

What the key gives you: React Router gives every navigation a location with a unique `key`, including Back/Forward and `navigate()`. If you store which location the drawer was opened on, "is it open?" is computed during render: `const navOpen = navOpenAt === key;` When the user navigates, `key` changes, the comparison is `false`, and the drawer is closed in the same render as the new page. There's no effect, no flash, and no per-link handlers.

The bug in my step 1 code: History entries keep their key. So: 1. Open the drawer on the Dashboard (key `a`), so `navOpenAt = "a"`. 2. Tap Calendar (key `b`). The drawer closes, but `navOpenAt` is still `"a"`. 3. Press Back. You're on key `a` again, `"a" === "a"`, and the drawer pops back open.

The fix is to forget the old key once you leave it:
[code truncated: 6 lines — adds `if (navOpenAt !== null && navOpenAt !== key) setNavOpenAt(null);`]

Calling `setState` during render is fine here. React allows it when it's guarded by a condition that stops after one pass (React's docs call this "adjusting state when a prop changes"). `App.tsx` already does the same with `if (user && authView !== "login") setAuthView("login")`. It still happens in the same render, so there's still no flash.

[Tables listing each test's behavior and mechanism, truncated in format; content: tab switching via `listDocuments` call counts; collapse via `aria-expanded`/`inert`; narrow start via stubbed `matchMedia`; pending reply via `<article>` count and `toBe(message)`; focus via `toHaveFocus()`; resize via `mockCompactScreen` inside `act()`; AppShell tests via attributes, `getByRole("dialog")`, `toHaveFocus()`, `fireEvent.keyDown`, and `MemoryRouter` history.]
