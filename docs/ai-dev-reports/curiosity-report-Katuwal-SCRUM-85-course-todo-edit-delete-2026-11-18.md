### AI
It’s a **possible edge case**, not a bug in the backend’s idempotency handling.

The creation key only prevents duplicates when the same key is sent again:

1. The form generates a random key and keeps it in a React ref while it’s mounted.
2. The backend creates the task with that key. If the same request is retried with the same key and details, it returns the existing task instead of creating another.
3. If the page reloads, the ref is lost. If the user then manually re-enters and submits the task, the form generates a **new key**. The backend sees a new request identity and creates a second task. It doesn’t deduplicate based on matching title, course, and due date.

So a reload alone doesn’t create a duplicate. The edge case is: **the first request was saved, its success wasn’t seen by the user, and after reloading they submit the same task again with a new key.** If the task is visible after reload and the user doesn’t resubmit it, there’s no duplicate.

The backend behavior is in [TodoListCreateView](C:/Users/crisu/Desktop/CS3398/studyforge/backend/apps/courses/views.py:104); the form’s key is held in memory in [TodoForm](C:/Users/crisu/Desktop/CS3398/studyforge/frontend/src/components/todos/TodoForm.tsx:21).

Yes—**sessionStorage can cover the reload edge case**, as long as it stores a *pending attempt’s random creation key*, not a permanent key for the task’s title/course/date.

The flow would be:

- Save the random key and the task details it belongs to in `sessionStorage` when submitting.
- If the page reloads before the user sees success, reuse that key when retrying the same details. The backend returns the already-created task rather than making another.
- Clear the stored key after the retry succeeds. A later intentional submission of an identical task then gets a fresh key and creates a new task.

So, **keeping the same key forever could block an intentional duplicate**: the backend treats a matching key and payload as the same request. The key must be scoped to an unresolved attempt and cleared once that attempt is confirmed. `sessionStorage` survives a reload in the same tab, but not closing that tab; it’s not a complete guarantee for every interrupted request.
