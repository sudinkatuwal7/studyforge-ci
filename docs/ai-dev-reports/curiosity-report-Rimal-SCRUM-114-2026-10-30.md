Linking would happen once, inside `POST /api/v1/auth/google/`, the first time that person signs in with Google. Nothing happens ahead of time, and it doesn't depend on which button they press (login and sign-up use the same endpoint).

#### The exact sequence in that request

1. **Check the token** (signature, `aud` = our client ID, issuer, expiry). If any check fails, return 401 and change nothing.
2. **Look up by Google `sub`.** This is Google's permanent user id. If a user already has this `sub`, log them in. That user was linked earlier, and we're done.
3. **Otherwise, look up by email** (ignoring case). **This is the linking moment.** It only happens if all of these hold:
   - `email_verified` is true
   - Google is authoritative for the address: it's `@gmail.com`, or the token has an `hd` claim (a Google Workspace domain). For other addresses, Google only verified the email when the Google account was created, and it may have changed hands since.
   - the account is active
   - the account isn't already linked to a *different* Google `sub`

   If all pass, we save the `sub` on the user and log them in, inside one transaction. If any fail, we return a clear error and change nothing.
4. **Otherwise, create a new user** with the `sub` saved.

This means storing the Google `sub`, either as a nullable unique field on `User` or in a small `SocialAccount` table. That needs a migration. Matching on email alone isn't enough, because a Google account's email can change.

#### A problem with linking automatically

I recommended automatic linking earlier, but I missed a risk. Our registration never checks that the person owns the email address. That allows an attack called **account pre-hijacking**:

1. An attacker registers `victim@gmail.com` with a password they choose.
2. Later, the real owner clicks "Continue with Google". We link to that account, and the owner starts studying in it.
3. The attacker still knows the password and can read everything.

Google proves who owns the email. Our password account doesn't. So linking automatically, with nothing else, isn't secure enough to meet the "handled securely" criterion. There are two safe options:

| Option | At the linking moment | Trade-off |

why are we verifying google token in google.py instead of view

### AI
Keeping it separate gives each file one job, and it's what makes the tests above possible. It wasn't strictly required, though.

**1. Each file deals with one thing.**
- `google.py` answers one question: is this a real Google token for our app, and who does it belong to? It knows about the google-auth library, `GOOGLE_OAUTH_CLIENT_ID` and Google's claim rules.
- The view answers different questions: which StudyForge account is this, should they get in, and what goes in the response and cookie? It knows about HTTP, the `User` model and JWTs.

If verification were inside the view, `post()` would mix Google-specific rules with account rules, and it would be harder to see the 401/403/409/503 decisions at a glance.

**2. The view doesn't depend on google-auth's exceptions.** google-auth reports problems with `ValueError`, `GoogleAuthError` and `TransportError`. `ValueError` in particular is very general: inside the view, a `ValueError` from a bug in our own code would be indistinguishable from a bad token. `google.py` turns those into our own two exceptions:
- `InvalidGoogleCredential`, which becomes 401
- `GoogleSignInUnavailable`, which becomes 503

The view only deals with those two. If we ever switch libraries, only `google.py` changes.

**3. All the security checks live in one place.** Checking the audience, requiring `email_verified is True`, and requiring `sub` and `email` are all in one function. Option B means we'll probably need a "link Google account" endpoint on the profile page later. That endpoint will call `verify_google_credential()` and get exactly the same checks. If the checks lived in this view, the second endpoint would have to copy them, and a missed `email_verified` check is the kind of mistake that leads to account takeover.

**4. It makes the tests possible without contacting Google.** Every test patches one spot, `apps.users.google.id_token.verify_oauth2_token`. That fakes only Google's network check and signature check. The rest of our code runs for real: the client-ID check, the `email_verified` rule and the exception conversion. If we patched the whole verify function instead, those rules would go untested.
