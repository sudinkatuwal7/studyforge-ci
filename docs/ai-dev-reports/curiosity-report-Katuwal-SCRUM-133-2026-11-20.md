Because in OCI, **permissions belong to the user, not to the key**. A Customer Secret Key can do everything its user can. The worker needs fewer permissions than Django, so it has to be a different user. One shared user = one permission set, and the worker would inherit Django's full write and delete rights.

## What each side actually needs

| | Django | Worker |
|---|---|---|
| Read documents | yes | yes |
| Upload new documents | yes | **no** |
| Delete documents (user removes material) | yes | **no** |

The worker only ever reads a file, checks its SHA-256 and extracts text. Write/delete would be permission it never uses.

## Why it matters here

1. **The worker is the riskiest part of the system.** It opens and parses PDFs, DOCX and PPTX uploaded by users — file parsers are a classic attack target. If a malicious file ever exploited the parser, the attacker gets whatever the worker's key allows. With read-only keys: they can read documents. With Django's keys: they could also **delete every student's materials or replace them with poisoned files**.

2. **They run in different places.** Django runs on the API VM; the worker will run on Sanish's OKE cluster. Each key lives somewhere different, so each is a separate chance of leaking. A leaked worker key should do as little damage as possible.

3. **You can revoke one without breaking the other.** If the worker key leaks, delete and replace just that key — uploads keep working. With a shared user you'd have to rotate Django's key too, interrupting uploads.

4. **The audit log becomes useful.** OCI's audit log records which user made each request. With separate users, "who deleted this object?" has a clear answer — and a delete by `studyforge-worker-svc` would be an obvious red flag.

## You've already seen the difference

Originally both keys were created under the Django user. Once authentication worked, our probe would have **failed** the "worker upload/overwrite/delete denied" checks — the "worker" key would really have had Django's permissions. After you moved the worker key to `studyforge-worker-svc`, OCI refused all three (HTTP 404 `NoSuchBucket`) and the probe confirmed the object was unchanged. That's the separation working.

## Trade-off
More admin: 2 users, 2 groups, 4 policy statements, 2 keys to rotate — small for this protection. A later improvement could be **OKE workload identity** for the worker: the pod authenticates as itself through an OCI dynamic group, so there's no stored worker key to leak at all. That'd be part of Sanish's deployment, not SCRUM-133.

## The same delete succeeds with Django's key
At the end of the probe, Django ran the identical `DeleteObject` on the same bucket and object — and it **succeeded** (the object then returned 404 on HEAD). Same bucket, same operation, different user, different result. That leaves the user's permissions as the only explanation.

## Why Oracle says "not found" instead of "access denied"
OCI deliberately answers "not authorized" and "doesn't exist" the same way for requests without permission. Its native API calls this error `NotAuthorizedOrNotFound` — so an attacker with a weak key can't probe which buckets/objects exist. The S3-compatible layer maps it to `NoSuchBucket`. Misleading at first, but intentional.

## The test checks the outcome, not just the error code
Because the code is ambiguous, I didn't let the test trust it alone. After the worker's attempts it checks that:
- the probe object still exists with the **same SHA-256** — not deleted or overwritten;
- the worker's attempted new key **does not exist** — the upload really didn't happen.

Even if OCI returned some odd code for another reason, a write or delete that actually happened would fail the test.

## If you want direct proof of the reason
OCI's **Audit** service (*Observability → Audit*) records Object Storage API calls, including denied ones, with the caller's user. Filtering on `studyforge-worker-svc` around the probe's time should show the `DeleteObject`/`PutObject` attempts as failed for that user — IAM's own record rather than our inference. Object-level events may need Object Storage logging enabled on the bucket; if they don't appear, that's the likely reason. It's a read-only console check you can do if you want that evidence for your report.
