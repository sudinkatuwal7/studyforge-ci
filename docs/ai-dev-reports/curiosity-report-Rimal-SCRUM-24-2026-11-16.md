**Whichever attempt finishes first wins.** If the old attempt finishes after the retry has started, but before the retry finishes, the old attempt's answer is the one kept.

**Step by step**

| Time | What happens | Question row |
|---|---|---|
| T0 | Attempt A starts | `PENDING`, `attempted_at=T0` |
| T0 + 2 min | History shows it as `FAILED` (nothing is written) | still `PENDING`, `T0` |
| T1 | Student retries → `start_retry` | `PENDING`, `attempted_at=T1` |
| T2 | **A finishes** → `save_answer` locks the row and sees `PENDING`, not `ANSWERED`, so it saves A's reply | `ANSWERED`, reply = A |
| T3 | **Retry B finishes** → `save_answer` sees `ANSWERED` and returns A's reply unchanged; B's result is thrown away | unchanged |

B's response is built from the saved reply (`answer_and_save` reads it back), so the retrying client receives A's answer. That matches what history shows after a refresh. If B finishes first, the roles swap: B's reply is saved, and A's late response, if any client is still listening, returns B's reply.

If A **fails** instead of finishing, `mark_failed` only matches `attempted_at=T0`. The row now holds `T1`, so nothing changes and the retry carries on.

**Two consequences**

1. **The answer may come from the older source selection.** A retry can send different `document_ids`. If A wins, the answer and its citations come from A's sources, not the ones the student picked for the retry. The citations are still accurate, since they point at the documents actually used, but the student may be surprised.
2. **The retry's AI call is wasted.** B's result is thrown away. That costs one AI call, but no data is lost.

**How the frontend will open an authenticated file**

The API authenticates with a token in the `Authorization` header, not a cookie. A plain link or `<a href>` can't send that header, so the frontend has to download the file itself:

1. **Unavailable citation** (`available: false`): show "This source is no longer available" and don't request anything.
2. **PDF:**
   - In the click handler, open a blank tab straight away. Browsers block `window.open` as a popup if it runs after an `await`, so this has to happen before any network request.

- Access tokens last 15 minutes and refresh 60 seconds before they expire.
- An answer can take over 2 minutes.

So if the token refreshes mid-answer and the answer finishes more than 60 seconds later, the refresh is sent with an expired token. It gets a 401, fails silently, and the title stays "New chat" until the next answer.

**Also minor:** two overlapping refreshes could apply in the wrong order. That only affects the order for a moment, never titles.

**Proposed fix**

```ts
const refreshRun = useRef(0);
async function refreshThreads() {
  const run = ++refreshRun.current;
  const shownBefore = new Set(threadsRef.current.map((item) => item.id));
  try {
    const all = await listConversations(tokenRef.current, lifetime.current.signal);  // latest token
    if (run !== refreshRun.current) return;                                          // a newer refresh wins
    const shownNow = threadsRef.current;
    const fresh = all.filter((item) => item.course_id === courseId && shownNow.some((s) => s.id === item.id));
    const freshIds = new Set(fresh.map((item) => item.id));
    // Created after the server answered, so not in its list yet: keep them.
    const createdMeanwhile = shownNow.filter((item) => !shownBefore.has(item.id) && !freshIds.has(item.id));
    setThreads([...createdMeanwhile, ...fresh]);
  } catch { /* titles stay as they are */ }
}
```
