### STUDENT
persisted retry mechanism like?

### AI
A lightweight option is a **database-backed deletion queue**—often called an outbox:

1. In the same database transaction that deletes the document and its related records, insert a cleanup row containing the storage backend and PDF key.
2. After commit, try to delete the PDF. A periodic management command or worker also checks for pending cleanup rows and retries failures.
3. Once deletion succeeds—or the file is already missing—remove the cleanup row.

The cleanup row matters: if the process crashes after the database commit but before the delete callback runs, the pending row is still there for a later retry. The callback can make cleanup happen sooner, but shouldn’t be the only record that work remains.

This is a small table plus a retry command, not necessarily a full queueing system. The trade-off is that PDF deletion may be delayed, and you need to retain the storage key until cleanup finishes.
