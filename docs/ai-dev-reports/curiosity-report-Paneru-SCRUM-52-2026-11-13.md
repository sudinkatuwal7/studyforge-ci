## 3. Edge cases

- **Double answer or two tabs:** each answer runs in a transaction that locks the session row (`select_for_update`). The client must send the `question_id` it is answering, and `UNIQUE(session, question)` is a final backstop. Without the `question_id` check, a double click would silently answer question 2 with the option picked for question 1.
- **Game over:** at 0 lives the status becomes `GAME_OVER` and `ended_at` is set. The result is saved in the same transaction, and every later answer gets `SURVIVAL_SESSION_ENDED`.
- **Wrong answer on the last question with 1 life:** the result is `GAME_OVER`, not `COMPLETED`. Running out of lives wins over running out of questions, and a test will lock this in.
- **Another student's session:** every lookup filters on `quiz__owner=request.user`, so GET and answer both return 404. Starting a session on someone else's course or documents is also 404.
- **Refresh:** GET rebuilds the state from the database, so lives, score and current question come back the same.
- **Hidden answers:** a correct option and explanation are only returned in the response to the answer for that question. Later questions' answers never leave the server.
- **Other paths that could leak answers:** normal submit on a Survival quiz is blocked with 409. `/quizzes/{id}/` shows question text but no answers, so I'd leave it as is. `/results/` only exists once the session has ended.
- **Abandoned sessions:** they stay `ACTIVE` and don't appear in history. I'm treating cleanup as out of scope.
- **Bad input:** an option index out of range, or `null`, returns 400 and costs no life.

## Stale tabs and decision 4

A **stale tab** is a browser tab showing old information because the server has moved on and the tab doesn't know.

1. A student opens the same Survival game in tab A and tab B. Both show **Question 3**.
2. In tab A they answer Q3. The server records it and moves to **Q4**.
3. Tab B still shows Q3. The student clicks an option there.

If the request only carried the option index, the server would apply it to **Q4**. The student would lose a life on a question they never saw.

Decision 4 makes the client say which question it is answering: `{question_id: Q3, selected_option_index: 2}`. The server sees that the current question is Q4, rejects the request with `409 QUESTION_NOT_CURRENT`, and sends back the current state. Tab B then shows Q4. No life is lost and nothing is recorded twice.

## Double answers and two tabs

"Double answer" means two requests for the same question reach the server. This happens in three ways:
- **Double click:** two fast clicks send two POSTs.
- **Network retry:** a slow connection makes the browser or the student resend.
- **Two tabs:** the case above.

When two requests arrive at almost the same moment, the row lock makes them run one after the other. The first one wins and moves the game to Q4. The second one then fails the `question_id` check (Q3 is no longer current) and gets a 409. If anything slipped past both, `UNIQUE(session, question)` stops a second answer row at the database level.

## Refresh, and how GET rebuilds the state

"Refresh" means anything that wipes the page's memory: F5, closing and reopening the tab, a phone killing the browser, or the token refresh logging the student back in. All the React state is gone.

The frontend keeps only the **session id**, in the URL (for example `/survival/42`), and calls `GET /survival-sessions/42/`. The server then:
1. loads the `SurvivalSession` row, filtered to the logged-in user;
2. reads `lives`, `score`, `status` and `current_position` straight from that row;
3. loads the question at `current_position` and sends it without its answer.

The browser holds nothing the server trusts, which is the point of the ticket. Editing JavaScript variables can't reset lives, because the next GET reads them from the database again.

One trade-off: if the student refreshes while the "Wrong! The answer was B" feedback is showing, they come back to the next question and that feedback is gone. That's acceptable for now. A `last_answer` field could be added later if the frontend wants it.

## How one student could reach another's session

Session ids are sequential integers. A logged-in student can:
- change the URL from `/survival/42` to `/survival/41`, or
- call the API directly with their own valid token and someone else's id, using curl, Postman or the browser dev tools.

Their token proves who they are, but not that the session is theirs. Every lookup therefore filters on `quiz__owner=request.user`. Someone else's session looks exactly like a session that doesn't exist, so they get **404**, and they can't even learn that session 41 exists. The tests will cover GET and answer with user B's token on user A's session: both return 404, and A's lives and score stay the same.

## Adding a missed question from a regular quiz

It's a good idea, because retrying something you got wrong is one of the best ways to learn. But it doesn't belong in SCRUM-52. I'd make it a follow-up ticket, for these reasons:

1. **Cheating loophole.** Taking a question from an unsubmitted ("abandoned") quiz would reveal its answer during Survival. The student could then go back and submit that regular quiz knowing the answer. So only questions from submitted quizzes would be safe to use.
2. **Free points.** For submitted quizzes, the results page has already shown the answer and explanation. The question becomes a free point unless it's left out of the score.
3. **Model conflict.** Each `Question` belongs to one quiz. A Survival quiz pointing at another quiz's question would make its results show a question from a different quiz. The clean fix is to *copy* the question into the Survival quiz, which is more design work.
4. **Scope.** None of the acceptance criteria need it, and adding it makes review harder for Nischal.

## The implementation problems, explained more clearly

**1. The quiz and the session are saved in two separate steps.**
Starting Survival does two things: it asks the AI for questions and saves them as a quiz, then it creates the Survival session that tracks lives and score. The existing quiz code saves the quiz on its own, so the session is saved just after.

If the server crashed in the moment between those two saves, a quiz would exist with no session attached. That does no harm. The student never got its id, so nobody can open or play it. It's just an unused row.

Saving both together would mean keeping the database open while the AI thinks for 5–10 seconds, which would slow things down for every other user. A rare unused row is the better trade.

**2. The tests can't fully reproduce two clicks landing at exactly the same moment.**
The double-answer protection matters most when two requests reach the server at the same instant. Django's normal tests run one request after another, so they can't produce that.

I'll test what can be tested reliably:
- Answering the same question twice in a row: the second answer is rejected.
- Trying to save a duplicate answer directly: the database refuses it.

A true at-the-same-instant test needs threads and a special test class. Tests like that tend to pass or fail at random, so I'd leave it out unless you want it.

**3. The lock that stops simultaneous answers only works on Postgres.**
When an answer comes in, the code locks the session so a second answer has to wait its turn. Postgres supports this. SQLite, the small file database (`db.sqlite3`) some local setups use, ignores the lock.

This doesn't matter in practice: the real app and `check.py` both use Postgres through Docker. Just don't treat a SQLite run as proof the double-answer protection works.

**What changed**
