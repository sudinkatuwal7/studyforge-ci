how does the Features link scroll to its section

### AI
The scroll is done by the effect in `LandingPage`, not by the browser. The browser only jumps to a `#section` on a full page load, and React Router clicks don't load a page.

#### The pieces

1. **The link.** `SiteHeader` renders `<Link to={{ pathname: "/", hash: "features" }}>`, which becomes `<a href="/#features">`.
2. **The target.** The features section has `id="features"`. `landing.css` gives it `scroll-margin-top: 1.5rem`, which leaves a small gap above the heading after the scroll.
3. **The effect** in `LandingPage`:
   ```tsx
   const { hash, key } = useLocation();
   useEffect(() => {
     if (!hash) return;
     document.getElementById(decodeURIComponent(hash.slice(1)))?.scrollIntoView();
   }, [hash, key]);
   ```
   React runs an effect after the page has been updated, so the section already exists when `getElementById` looks for it.

#### What happens on a click

1. The user clicks Features.
2. React Router cancels the browser's normal link behavior (`preventDefault`). It adds a history entry for `/#features` with a **new `location.key`**. There's no page load, so the browser never scrolls by itself.
3. `App` re-renders with the new location.
4. The effect runs, finds `#features`, and calls `scrollIntoView()`. The default lines the section up with the top of the page, using the margin from step 2 of the pieces, and jumps without animation.

#### How each case reaches the effect

| Where the user clicks Features | Why the effect runs |
|---|---|
| **`/login` or `/register`** | The route changes to `/`, so `LandingPage` mounts. Effects run on mount, and the hash is `#features`. |
| **Already on the landing page** | `LandingPage` stays mounted, but `hash` changes from `""` to `"#features"`, so the effect runs again. |
| **Clicked a second time** after scrolling away | `hash` is still `"#features"`, but `key` is new, so the effect runs again. Without `key` in the list, the second click would do nothing (a mutation check confirmed this). |
| **The login card at `/` after a sign-out** | The new key ends the notice in `App` (`sessionEndedAt !== location.key`). The landing page mounts and the effect runs on mount. Both happen from this one click. |

#### Reload, a shared link, or Ctrl+click on `/#features`

This is a real page load, which the effect also handles:

1. The browser tries to scroll to `#features` straight away, but React hasn't rendered yet, so the element doesn't exist and nothing happens.
2. `App` first shows "Checking your session...". `LandingPage` isn't mounted yet.
3. The session check finds no session, so `LandingPage` mounts. The effect runs on mount with `hash = "#features"`, and the page scrolls.

If the visitor turns out to be **signed in**, `/#features` shows the dashboard. `LandingPage` never mounts, so nothing scrolls, which is correct.

why do we need both hash and key

### AI
They answer different questions. `hash` says **where** to scroll (and whether to scroll at all). `key` says that **a new navigation happened**. Neither one alone is a reliable trigger.

#### `hash` alone: a repeat click doesn't scroll

React reruns an effect only when a value in its dependency list changes.

1. The first click on Features changes `hash` from `""` to `"#features"`, so the effect runs and the page scrolls.
2. The user scrolls back up and clicks Features again. React Router adds a new history entry, but `hash` is still `"#features"`. Nothing in the list changed, so the effect doesn't run and the page stays where it is.

`key` fixes this, because React Router gives every navigation a new key, including a repeat of the same URL. The mutation check confirmed it: with `[hash]` only, "scrolls each time the Features link is clicked on the page" failed.

#### `key` alone: it works today, but for the wrong reason

I tried `[key]` in scratch just now and restored the file afterwards.

- **All 22 tests still pass.** Every in-app click changes `key`, so the tests can't tell the two versions apart.
- **Lint warns:** `react-hooks(exhaustive-deps): React Hook useEffect has a missing dependency: 'hash'`. The rule exists because an effect that reads a value but doesn't list it can miss changes to that value.
- **`key` doesn't always change when `hash` does.** In the installed `react-router` source, a history entry the browser creates itself, such as typing `#features` into the address bar, gets the key `"default"`. The first page load also has the key `"default"`. So `hash` can change while `key` stays the same, and an effect listing only `key` wouldn't run.
  - In that particular case the browser scrolls by itself, because the section is already on the page, so in practice nothing breaks.
  - But this is luck, not design, and the tests wouldn't notice if it stopped being true.

#### Summary

| Dependencies | First click | Repeat click | Browser-made hash change | Lint |
|---|---|---|---|---|
| `[hash]` | Scrolls | **Doesn't scroll** | Runs | Clean |
| `[key]` | Scrolls | Scrolls | **Doesn't run** (the browser scrolls instead) | **Warning** |
| `[hash, key]` | Scrolls | Scrolls | Runs | Clean |

The general rule: list every value the effect reads (`hash`). Then add `key` to say "also run on every navigation", which is the extra behavior we want.

**What the tests don't cover:** no test catches removing `hash` from the list, because jsdom can't reproduce a hash change the browser makes by itself. Lint is what guards that. If you want it in the browser check, type `/#features` into the address bar while you're already on `/`.
